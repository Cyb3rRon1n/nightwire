# Nightwire — Roadmap

A cyberpunk tabletop RPG with an AI game master, playable solo or with friends, in a real browser. A ground-up sibling project to `oracle` (the owner's D&D-flavored AI-DM project) — same underlying idea (an LLM running a real, rules-grounded tabletop game), different genre, different platform, built fresh rather than adapted, deliberately.

This file is the durable source of truth for project state and decisions, same convention `oracle/ROADMAP.md` already established — kept thorough enough that picking this repo up cold (a new machine, a new AI coding session) is enough to continue without re-deriving context.

## Why a fresh project, not an oracle fork

Oracle's engine, protocol, and reliability-tested narrator patterns are genre-agnostic in principle, but the owner chose a full rebuild over reusing that plumbing — a deliberate call, not an oversight, made explicitly during this project's design conversation (2026-08-22). The stated reasoning: a from-scratch build lets nightwire's architecture serve its own identity rather than carrying oracle's D&D-shaped decisions forward, and doing it this way is itself part of what makes the project worth building.

**What still carries over is lessons, not code:**
- Structured JSON output beat native tool-calling for local-model reliability on the mechanical decision step (roughly doubled real tool-call correctness in oracle's own testing) — worth trying first here rather than re-discovering it.
- A silent self-correction pass (the DM gets one quiet chance to fix a narration that should have changed game state before a player-visible advisory fires) was a real, validated pattern worth carrying forward conceptually.
- Every reliability claim in oracle was backed by a live, repeatable measurement harness (`--repeat N` against a real model), never a single anecdotal run — the same discipline applies here.
- Real infrastructure verification (a live model, a live browser, a live multiplayer session) over mocked-only claims of "done."

## Platform decision (2026-08-22)

A pure terminal client cannot deliver this project's stated destination (real character art, TTS narration, a rich visual tabletop-style sheet) — no reliable inline-image support across terminals, and critically, **a remote/SSH terminal session has no channel to play audio on the user's own machine at all**. Confirmed against four comparable open-source AI-DM projects (`dungeon-ultimate`, `open-dungeon`, `skeinkeeper`, `dungeon-master-ai`) — all four independently left the terminal for a browser or desktop-web frontend once they wanted the same things; none stayed TUI-only for this feature set.

**Decision: a real browser-based web client from the start**, talking to a Python backend over WebSocket — justified by multiplayer bidirectionality specifically (player actions in, broadcasts out, at real-time cadence), not narration streaming alone (2026 consensus treats SSE as the default for one-way streaming; see `docs/superpowers/specs/2026-08-22-core-engine-design.md`'s transport section) — no terminal client planned for this project.

**Primary reference: `open-dungeon`** (github.com/newideas99/open-dungeon, MIT, 216 stars) — chosen by the owner as the closest match to the desired feel. Concretely useful, verified patterns worth building on (not forking the repo itself — see "What we're not doing" below):
- **Do/Say/Story-style input composer**: a three-way mode toggle that formats the player's text client-side before sending (`"do"` → `"> draw my sword"`, `"say"` → `'> You say "..."'`) — no protocol-level mode field, just a text transform. Nightwire's own version drops "Story" (co-writing narration isn't part of the current design) in favor of **Do / Say / Think**.
- **Chat-bubble narration** via plain flexbox alignment (player right-aligned, GM/NPC left-aligned) — no bubble component library needed.
- **A generated image as a field on the message/turn object itself**, rendered inline under that turn by the message component — the shape nightwire's own future image-gen phase should copy.
- **Per-stage swappable local/cloud backends** (narration/image/audio each independently local-or-hosted) — an independently-verified real pattern (`dungeon-ultimate`'s own per-stage local/cloud toggle, found in the four-project prior-art research), generalized across all three media types from day one instead of retrofitted later.

**Superseded 2026-08-23 — see below.** This section originally said cloning open-dungeon's repo was explicitly out of scope; that call was reversed after Phase 4a hit real friction building the frontend from scratch (a `react-use-websocket` CJS/ESM interop bug under Vite that cost a long debugging cycle). The owner decided to adopt open-dungeon's actual repository as the new frontend base instead, to rework into nightwire's own shape over time, rather than keep building from zero. Original reasoning, kept for the record: its genuinely reusable code (the composer's format function, a few div/flexbox patterns) looked small enough to reimplement directly, and its Next.js API routes / SQLite backend / 3,991-line single-file monolith looked like baggage not worth taking on. That tradeoff is being revisited now that the from-scratch cost has been felt directly, not just estimated. Framework changes accordingly: **open-dungeon's own Next.js + React 19 + SQLite stack**, not Vite — nightwire's Python backend (WebSocket protocol, already built through Phase 3b) still owns all real game logic; open-dungeon's Next.js API routes / SQLite layer will need to be stripped or bypassed in favor of talking to that real protocol, tracked as its own implementation plan (Phase 4a-revised).

## Ruleset decision (2026-08-22)

**Homebrew original cyberpunk ruleset, not adapted from an existing system.** Researched real alternatives first, same diligence oracle's own `ATTRIBUTION.md` applies to the D&D SRD:
- No dedicated open-licensed "cyberpunk SRD" exists as its own project.
- **Cypher System Open License (CSOL)**, Monte Cook Games — a real, verified, CC-BY-equivalent right to reproduce Cypher System rules text in a derivative product. Legally solid, but Cypher is a genre-agnostic light system (Might/Speed/Intellect pools) — would need a full reskin into cyberpunk flavor, not cyberpunk out of the box.
- **CY_BORG** (a MÖRK BORG hack) has real cyberpunk flavor and a real third-party license permitting derivative products, but whether that license actually grants reproduction of its core rules TEXT (vs. only permission to make a referencing/compatible product) could not be confirmed from the public license pages alone — an unresolved, unverified risk.
- **Cyberpunk RED/2020** (R. Talsorian) confirmed not openly licensed at all — ruled out.

Given the owner's own stated motivation ("that in itself will make this unique"), homebrew was chosen over the CSOL reskin path or the unverified CY_BORG path — zero licensing risk, and originality is treated as a real feature here, not just a fallback. This means nightwire's core mechanics (dice system, attributes, roles/classes, gear/cyberware, hacking resolution, combat resolution, NPC stat blocks, advancement) are **not yet designed** — this is real, first-priority design work, tracked as Phase 1 below, not something this roadmap resolves on its own.

## Phases

Each phase gets its own brainstorming pass (questions → approaches → design → spec) and its own implementation plan when its turn comes — this roadmap sequences them, it doesn't pre-design them.

1. **Cyberpunk ruleset design** (designed 2026-08-22, implemented 2026-08-22) — the new "SRD": core dice/resolution mechanic, attributes, roles/classes, combat resolution. Full design in `docs/superpowers/specs/2026-08-22-cyberpunk-ruleset-design.md`, implementation plan in `docs/superpowers/plans/2026-08-22-phase1-ruleset-implementation.md`. Real code and tests: `ruleset/{attributes,difficulty,lifepaths,resolution,roles}.py`. Cyberware/gear and hacking mechanics from the original design scope are not yet built — advancement/leveling isn't either, tracked as open ruleset scope, not a Phase 5+ concern.
   - **Core mechanic**: `1d10 + attribute + skill` vs. DC, three outcome bands (clean success / success-with-complication / failure) — CY_BORG's simplicity plus The Sprawl's tiering. Dice-pool systems (Shadowrun, Neon City Overdrive, Interface Zero, Genesys) were independently surveyed and each flagged medium/high tool-call complexity (variable pool size, success-counting, rerolls) versus the flat single-die-plus-modifiers systems (CY_BORG, Cyberpunk RED) — a real finding from that survey, not an oracle citation.
   - **Six attributes** (Body/Reflexes/Tech/Cool/Intellect/Presence), same modifier-formula shape as D&D's ability scores.
   - **Four starting roles, now research-locked** (updated 2026-08-22): **Solo / Netrunner / Techie / Fixer**, plus a separate **Lifepath** axis (Nomad / Streetkid / Corpo, narrative background only, zero mechanical weight). The gap flagged above got a real answer: a TTRPG-focused deep-dive first argued for 6 (finding Medtech mechanically distinct from Tech, and Infiltrator a real gap per The Sprawl) — but checking Cyberpunk 2077 itself, the project's own explicit aesthetic touchstone, pulled back to 3 official archetypes (Solo/Netrunner/Techie) with no dedicated medic build at all and stealth as cross-cutting perks, not a hard class. Final call weights the touchstone for the "hard class" question and keeps Fixer independently — a TTRPG rolling real dice for persuasion needs it in a way a video game's scripted dialogue never had to. "Tech" renamed to **Techie**, CP2077's own name for that exact archetype. Full reasoning and citation trail in `docs/superpowers/specs/2026-08-22-cyberpunk-ruleset-design.md`'s Roles/Lifepath sections.
   - **Milestone leveling**, not XP-per-kill — avoids needing an invented-from-scratch XP-by-threat table for every enemy type.
   - **Content/backend**: full genre-typical grit by default (private tool, owner + friends), local-first LLM with a hosted API as a secondary option (known tradeoff: hosted play may refuse content local play wouldn't).
2. **Core engine** (designed 2026-08-22, implemented 2026-08-22–23) — full design in `docs/superpowers/specs/2026-08-22-core-engine-design.md`, implementation plans `docs/superpowers/plans/2026-08-22-phase2-engine-core-implementation.md` and `2026-08-22-phase2b-websocket-server-implementation.md`. New build, not adapted from oracle's files — see "Why a fresh project" above. Real code and tests: `engine/{session,character,turns,persistence}.py`, `server/{app,dispatch,connection_manager,views}.py`.
   - **The one deliberate improvement over oracle**: free-flowing action outside combat (no turn queue at all), strict initiative-gated turn order only once combat is formally declared. Oracle enforces a whole-session queue even for casual roleplay — research (real tabletop GMing convention, AI Dungeon's own multiplayer, MUD architecture) unanimously found that wrong: turn order is a combat-specific tool everywhere it was checked, never a session-wide rule. Not different for its own sake — a real, research-backed fix.
   - Session/character data model, redacted-public-view multiplayer privacy split, WebSocket+JSON protocol, swappable narrator backend (structured-output-first), JSON file-per-session persistence, and pytest-from-day-one testing all carry forward as *proven patterns*, freshly implemented — not as reused code.
3. **AI GM / narrator backend** (designed 2026-08-22, implemented 2026-08-23) — full design in `docs/superpowers/specs/2026-08-22-narrator-backend-design.md`, implementation plans `docs/superpowers/plans/2026-08-23-phase3a-narrator-engine-implementation.md` and `2026-08-23-phase3b-websocket-narrator-wiring-implementation.md`. Real code and tests: `narrator/{client,tools,harness}.py`, `server/narration.py`. `NarratorResponse.tool_call` was hardened to a Pydantic discriminated union on 2026-08-23 (`fix: constrain tool_args to a real per-tool schema, not a loose dict`) after live testing found the model calling `start_combat` with a plausible-but-wrong argument shape on nearly every turn.
   - **Default local model: Qwen3, 7-8B class** — not carried over from any prior project's own testing. Real grounding: the Berkeley Function-Calling Leaderboard (a real, current external tool-calling benchmark) plus current (2026) local-LLM guides characterizing Qwen2.5 as now "legacy" versus Qwen3's native tool-calling template and stronger reasoning.
   - **Not defaulting to an abliterated/"uncensored" model, despite the full-genre-grit content goal.** Real, specific evidence: abliterated variants show measurably weaker tool-calling performance than their base models, plus documented general capability loss (structured/math reasoning most sensitive). Abliteration suits pure creative-prose generation, not a narrator that must also reliably call tools — the opposite of what Nightwire needs from the same model in the same pass. Default instead: a standard Qwen3 instruct model with a permissive system prompt (already far less restrictive than any hosted API, since there's no external safety layer to fight at all); a genuine Dolphin-style fine-tune (retrained, not abliterated) stays a fallback only if real play-testing shows actual refusals.
   - Tool surface: `request_roll`, `apply_character_update`, `update_world` — derived directly from the ruleset and engine specs, not re-invented.
   - **`start_combat`/`end_combat` removed from the narrator's tool surface entirely, 2026-08-23** (root-cause fix, after four prompt/sampling fixes failed to resolve a real over-trigger — full investigation trail below). Combat start/end was already a fully real, functional **player-sent** message path the whole time (`server/dispatch.py` → `engine/turns.py`, real initiative rolls) — the narrator's own copy of these tools (`narrator/tools.py`'s `_execute_start_combat`/`_execute_end_combat`) was always a no-op stub, redundant with that real path from the start. Deleting it from `ToolCall`'s discriminated union means the model can no longer emit it at all, closing the bug at the schema level instead of continuing to prompt-tune a model bias that resisted every other fix.
     - **Investigation trail, most-to-least effective**: (1) restraint guidance + a positive/negative example pair in the system prompt (same technique that fixed `image_request`'s under-firing) — went from firing on every turn to 2/5 on a 5-turn live probe; (2) a stronger ordinary-movement counter-example + default-to-null tiebreaker — a second identical probe came back 5/5, worse; (3) suspecting the model was reading its own `[start_combat: {...}]` log-line acknowledgment back as narrative evidence combat was ongoing, filtered bracket-prefixed tool/image lines out of the "Recent events" context (`server/narration.py`'s `_build_messages`) — a third probe still came back 5/5; (4) suspecting default Ollama sampling temperature (~0.7-0.8 for Qwen3) was letting noise dominate the tool-choice decision, added `options={"temperature": 0.3}` to the structured-output call — a fourth probe still came back 5/5. All four are real, kept improvements (lower temperature and context filtering benefit every tool decision, not just this one) but none eliminated the over-trigger live — this was a temperature-resistant model prior, not a fixable prompt-wording bug. Removing the tool from the schema was the actual fix.
     - **Re-verified live, 2026-08-24, on a new local GPU deployment** (this machine now runs `ollama.service` + `image-server.service` + `nightwire-server.service`, no longer msi-laptop-only): a 3-turn probe including a deliberately combat-flavored action ("I draw my pistol and open fire...") produced zero `start_combat` calls and zero schema/validation errors — confirms the fix holds under real qwen3:8b generation, not just the unit tests (which only prove the schema rejects the tool, not that the model stops trying). Surfaced two new, separate findings while doing this: (1) the combat turn's `apply_character_update` call used `player_id: 'player'` (not the real `'p1'`) — caught safely by existing validation (`[tool error: unknown player_id: 'player']`, turn continued normally) but the intended health/inventory update never applied; unlike `request_roll`, whose `player_id` `server/narration.py` forces server-side, `apply_character_update`'s is trusted from the model — the same trust-boundary bug class already fixed once, but not blindly copy-paste-fixed here since (unlike a roll, which always targets the actor) a real multiplayer session may legitimately need this tool to target a teammate, so forcing it to the acting player needs a real decision, not a reflex. (2) `image_request` fired on all 3/3 turns in this pass, including one intended as a mundane-turn restraint check — but that turn's own narration introduced new visual detail (a service ladder, a fire escape, a drone), so it isn't a clean repro of the earlier documented 2/4 restraint result, and the temperature=0.3 change made for this same fix plausibly shifts `image_request`'s firing rate too since it's the same sampling call. Neither finding is fixed here — both are live-verified observations, not yet scheduled or actioned.
     - **Finding (1) fixed, 2026-08-24 — grounded, not forced.** Confirmed the id trust boundary is deliberate (`docs/superpowers/plans/2026-08-23-phase3b-websocket-narrator-wiring-implementation.md`: `apply_character_update` "legitimately targets a different character than the actor, e.g. narrating damage to an NPC or another player") — so the fix isn't `request_roll`'s force-to-actor pattern, which would silently break cross-player targeting. Real root cause instead: the model was never told what real `player_id`s exist at all, only able to infer one from a prior `"{player_id}: ..."` log line — so on a session's first turn (nothing yet to infer from) it invents a plausible placeholder like `'player'`. `server/narration.py`'s `_build_messages` now prepends a `Party (use these exact player_ids): p1 (Rook), ...` line built from `session.characters`, every turn — same grounding-example technique already proven for `image_request`'s under-firing and (differently) `start_combat`'s over-firing. Live-verified same day: a fresh session's very first action ("The wound is bad — apply the damage...") produced `[apply_character_update: {'player_id': 'p1', 'health': 7, 'armor': 0}]` — the real id, no tool error, health correctly applied 10→7.
     - **Finding (2) investigated and partly fixed, 2026-08-24.** The temperature=0.3 hypothesis was tested directly and **not supported**: a controlled A/B probe (same system prompt/context, 10 reps per condition on two clearly-mundane test actions, direct `ollama.chat` calls bypassing the full session) measured a 30% false-fire rate at temperature=0.3 versus 50% at the original 0.7 — if anything the lower temperature is *slightly* better on this decision, opposite of the hypothesis; temperature is unchanged. What the probe did confirm: false-firing on genuinely mundane turns is a real, persistent baseline behavior (30-50% depending on temperature) independent of the earlier documented "2/4 correct" result, which in hindsight was likely an underpowered n=2 read, not a settled number. Two fixes landed: (1) **structural cooldown** — `Session.last_turn_had_image` (new field, `engine/session.py`) tracks whether the previous turn generated an image; `server/narration.py`'s `handle_action` now refuses to honor `image_request` when it's `True`, resetting it every turn. This backs the model's own "never two turns in a row" instruction the same way `request_roll`'s forced `player_id` and finding (1)'s roster grounding back their rules — structurally, not by trusting prompt compliance alone (live probing had already found this rule violated 3/3 consecutive turns in one run). (2) **Two more counter-examples** added to `server/__main__.py`'s system prompt (checking own gear/inventory, routine combat in an already-described location) targeting the exact false-fire types the A/B probe caught — the underlying per-turn false-fire rate on novel mundane actions isn't structurally fixable the way the cooldown is, so this is a prompt-quality improvement, not a guaranteed fix (same caveat `start_combat`'s investigation found: an 8B model's decision noise doesn't fully yield to prompt wording). Live-verified: a fresh 3-turn probe (combat, mundane, new-location) fired 2/3 with no consecutive repeats, versus the pre-fix run's 3/3-with-a-violation.
4. **Web frontend** (Phase 4a-revised done 2026-08-23) — full design in `docs/superpowers/specs/2026-08-22-web-frontend-design.md`; the actual build followed a revised path, see below. Original design called for a from-scratch Vite + React 19 + TypeScript + Tailwind scaffold — built once (Phase 4a original), then scrapped after Task 7's live browser verification hit a `react-use-websocket` CJS/ESM interop bug under Vite that cost a long debugging cycle; **open-dungeon's actual repository (Next.js + React 19 + SQLite) is now the frontend base instead**, reworked over time rather than built from zero (see "Superseded 2026-08-23" above). An isolated `/nightwire` route talks directly to the real Python WebSocket backend, bypassing open-dungeon's own Next.js API routes/SQLite entirely — `docs/superpowers/plans/2026-08-23-phase4a-revised-implementation.md` has the full task-by-task record.
   - **Built and live-verified against a real GPU-backed narrator**: connect/join, a Do/Say/Think composer (client-side text transform, same pattern as open-dungeon's own Do/Say/Story — `think` mode's exact wording wasn't in the original spec, decided here), chat-bubble narration layout (own lines right-aligned, reusing open-dungeon's own bubble pattern verbatim), a persistent vitals/party/objectives band, a deterministic placeholder character portrait (initials+color, no real art yet), and an on-demand character sheet overlay (`Ctrl+K`).
   - **State split by kind, not one library for everything**: server-pushed state (character view) gets a thin WebSocket-message-to-reducer layer (`reducer.ts`), not Zustand — reaching for a client-state library for state that's actually server-authoritative solves the wrong problem.
   - **`react-use-websocket`**, `share: true`, exponential backoff with jitter on reconnect — the interop issue that killed the original Vite scaffold doesn't reproduce on the Next.js base.
   - **No test framework** — the real check is against the live backend (a real GPU-backed `qwen3:8b`), not a mock; Vitest/RTL/MSW were part of the scrapped scaffold and were not carried forward.
   - **Real character creation fields, built 2026-08-24**: Role and Lifepath were plain, unvalidated text inputs — the server never checked them against the ruleset's real roster (`ruleset/roles.py`'s 4 roles, `ruleset/lifepaths.py`'s 3 lifepaths) anywhere, so a typo or made-up value would silently pass `join`. Investigating surfaced a real, live consequence, not just a hygiene gap: `server/portrait.py`'s `_ROLE_VISUALS.get(character.role.lower())` silently drops the visual descriptor for any string that doesn't match one of the 4 known keys, quietly producing a blander portrait with zero feedback to the player. Fixed with `<select>` dropdowns in `frontend/src/app/nightwire/page.tsx`, backed by a small `ROLES`/`LIFEPATHS` constant that mirrors the ruleset's real name + description text — same duplication pattern `server/portrait.py`'s own `_ROLE_VISUALS`/`_LIFEPATH_VISUALS` already use for this exact key set, rather than adding a new REST endpoint to a WebSocket-first backend for static reference data. Selecting an option shows its description live. **Attribute point-buy stays explicitly out of scope** — no starting-attribute-generation mechanism exists anywhere in the ruleset yet (a real, separate Phase 1 gap; attributes still default the way they already did, unset and reading as 10 everywhere). Verified in-browser: both dropdowns list the correct real options and update their description text on selection.
   - **Other-player-vs-narrator bubble distinction, built 2026-08-24**: a player's own action log line is server-authored as `"{player_id}: {text}"`, and every other party member's real `player_id` is already a client-visible key of `StateView.characters` — so a teammate's line is distinguishable from narrator prose (including NPC `"Speaker: text"` segments, which key off an in-fiction name, never a real `player_id`) with a plain prefix check, no new protocol field. `frontend/src/app/nightwire/page.tsx`'s `otherPlayerName()` does that check; teammate lines now render as a left-aligned, muted bubble with a small name label above it (mirroring the viewer's own right-aligned bubble but visually deemphasized), while narrator prose keeps its existing unbubbled serif treatment. Live-verified in two real browser tabs against a real running backend (stubbed narrator response, no GPU needed): a teammate's `"Ghost"`-labeled bubble, plain narrator prose, and the pre-existing `[audio error: ...]` fail-soft line all rendered correctly and distinctly in the same log.
   - **Combat/turn-order controls, built 2026-08-24**: investigating the deferred item surfaced a real protocol gap, not just missing UI — the original `start_combat` message took a client-supplied `{player_id: roll}` dict for the *whole party* in one message, but `server/views.py`'s `build_view` redacts every character's attributes except the viewer's own, so no single client could honestly compute a real `1d10 + Reflexes` initiative roll (the ruleset spec's formula) for teammates. Fixed by moving the roll server-side: a new `roll_initiative` message (no payload) rolls only for the sending player, using `session.characters[player_id]` — which holds every character's real, unredacted attributes server-side — reusing the exact `1d10 + modifier(reflexes)` pattern `narrator/tools.py`'s `_execute_request_roll` already established. `Session.pending_initiative` accumulates rolls (`engine/turns.py`); once `set(pending_initiative) == set(characters)`, the existing `start_combat` locks in `turn_order` exactly as before. `end_combat` now unconditionally clears `pending_initiative` too, doubling as "cancel a declaration" if the fight fizzles before everyone's rolled. Each roll is also logged (`[initiative: {name} rolled {total}]`, reusing the `[image: ...]`/`[audio: ...]` bracket convention) so players see rolls land in real time with no new `StateView` fields needed. **Known, deliberate limitation**: no timeout — if a joined player never rolls, combat never locks, matching real tabletop convention (the GM waits for the table) rather than inventing a forced-start mechanism. Frontend: a "Roll Initiative" button, a turn banner (`is_your_turn`-driven), "End Turn" (gated to the acting player), and "End Combat" controls in `frontend/src/app/nightwire/page.tsx`. Live-verified in two real browser tabs against a real running backend (no GPU needed — the whole flow is pure engine logic, no narrator/image/TTS calls): two players joined, one rolled first (roster incomplete, combat correctly stayed unlocked), the second rolled and combat locked with the correct initiative-sorted turn order, turn-gated controls rendered correctly for both the acting and non-acting player, "End Turn" cycled the order, and "End Combat" restored the pre-combat state.
   - **Nightwire's own "Neon Noir" visual theme, built 2026-08-24**: `/nightwire` had inherited `open-dungeon`'s warm brown/cream fantasy-tabletop palette (`frontend/src/app/globals.css`'s shared `--background`/`--foreground` tokens, amber-200 buttons, stone-800 borders) by default, not by design — zero cyberpunk-specific styling existed. Brainstormed with the visual-companion tool against three grounded directions (CP2077's own corpo-neon HUD chrome, CY_BORG's harsh black/acid-yellow zine-punk graphic design, and a moodier Blade-Runner-esque indigo/violet duotone) — the third, "Neon Noir," was chosen. Implemented as `frontend/src/app/nightwire/theme.css` (a `.nw-theme`-scoped stylesheet, deliberately kept out of the shared `globals.css` so `open-dungeon`'s own routes are untouched): deep indigo/violet gradient background, a violet/cyan duotone (mirroring CP2077's own dialogue-color convention) plus a hot-pink `#ff4d6d` danger accent for combat state, Rajdhani (a real, license-clear Google Font already common in game HUD design) for headers/labels/HUD text, narrator prose kept serif for deliberate contrast against the glowing HUD chrome. `narrator/portrait.ts`'s placeholder-avatar palette got the same treatment (Tailwind arbitrary-value hex colors, still route-local). `frontend/src/app/nightwire/layout.tsx` (new) overrides the shared root layout's `"Open Dungeon"` tab title to `"Nightwire"` for just this route segment, via Next.js's own per-segment metadata layering — confirmed against the App Router's own docs, not assumed. Live-verified in-browser end to end (no GPU needed for the styling itself); real screenshots replaced the placeholder SVG mockups in `docs/images/screenshots/` and the README's own "Screenshots" section.
5. **Image generation** (built and live-verified 2026-08-23) — design in `docs/superpowers/specs/2026-08-23-image-generation-design.md`, implementation plan `docs/superpowers/plans/2026-08-23-phase5-image-generation-implementation.md`. `ImageBackend` protocol + `FluxWorkerBackend` (talks to `newideas99/ultra-fast-image-gen`'s worker, deployed on msi-laptop as `image-server.service`). Portrait generated once on `approve_character`, saved, used as a reference image for later scene generation (`[image: path]` log lines, same bracket convention tool results already use).
   - **Real, live-verified findings, not assumed**: the worker's own "fast" mode defaults to 1024px, which OOMs on an 8GB card (confirmed live) — `FluxWorkerBackend` now explicitly requests 512px, which fits and works. Reference-image consistency is real and visible, not just a benchmark citation: a second scene generation using the approved portrait as reference produced the same beard/jacket/build, correctly placed in a new setting.
   - **`image_request` restraint, live-verified 2026-08-23**: the narrator now knows the field exists and when to use it. A restraint-only prompt ("use it rarely") never fired once across a live 4-turn probe, including a genuinely new location — an unconstrained optional field defaults to null without a positive example. Adding one worked example + one counter-example fixed it: a 4-turn live probe fired on both new-location turns and correctly stayed silent on two mundane dialogue turns, never two in a row. ## Design already settled (carried over from the brainstorming session that spawned this project)

These were brainstormed and mockup-approved before nightwire had its own repo — captured here so they survive the move rather than needing to be re-decided:

- **Layout**: chat-bubble narration (dominant, top region) + a persistent compact vitals/party/objectives/combat band below it (always visible — no tab-switching hides your own HP) + an input bar at the bottom. A hybrid of two directions explored, not a copy of any single reference.
- **Full character sheet**: an on-demand overlay (opened via a keybind, e.g. `Ctrl+K`), laid out like a real physical tabletop sheet — boxed sections for core stats, saves/skills-equivalent, equipped vs. carried gear, features/abilities — not a flat scrolling list. Border/panel style: minimal thin single-line rules between sections, no heavy box-drawing borders, whitespace doing most of the separating.
- **Character portrait**: a small pre-drawn art placeholder (not photorealistic, not AI-generated yet) shown beside the sheet header, picked by character build — a real visual touch that ships before Phase 5's real image generation exists, deliberately cheap.
- **Input composer**: Do / Say / Think mode toggle, client-side text formatting only (see "Platform decision" above) — confirm exact formatting/labels during Phase 4's own design pass, since it was scoped conceptually here but not pixel/wording-finalized.
- **Secondary/utility commands** (equivalent to oracle's `/equip`, `/export`, etc.): stay as typed text for now, no command-palette widget in the first build — added only if it turns out to matter in practice.

## Explicitly not doing (yet)

- Reusing oracle's Python engine/protocol code directly — see "Why a fresh project" above.
- A terminal/TUI client — see "Platform decision" above.
- Adapting an existing ruleset (Cypher/CSOL, CY_BORG) — homebrew chosen instead, see "Ruleset decision" above.
- Full scene-image compositing (image drawn into a live map/scene) — even peer projects researched haven't solved this; Phase 5 targets per-turn cards instead.
- A persistence-backed session store for multi-worker deployment — `server/app.py`'s session dict is in-memory, single-process only (`# ponytail:`-flagged in the code). Fine for the current single-instance deployments (Fedora, msi-laptop); would need real work before running behind multiple server processes.
