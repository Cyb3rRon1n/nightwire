# Nightwire Core Engine Design — Phase 2

Status: designed, not yet implemented. Builds on `2026-08-22-cyberpunk-ruleset-design.md`. Every decision below is grounded in independent external research, cited per section — not carried over from oracle (the team's prior D&D-flavored AI-DM project) on the strength of oracle having done it that way. Where oracle happened to reach the same conclusion, that's coincidence confirmed by research, not the reasoning.

## Turn model — free-flowing outside combat, initiative-gated during combat

Real tabletop GMing convention, AI Dungeon's own multiplayer design, and MUD architecture were researched directly and unanimously found: turn order is a combat-specific tool, never a whole-session rule. Real tables run roleplay/exploration as free-flowing conversation; initiative order exists specifically "to keep a table from talking over each other when combat begins" ([D&D Beyond forum](https://www.dndbeyond.com/forums/dungeons-dragons-discussion/rules-game-mechanics/206332-combat-talking)). AI Dungeon's multiplayer explicitly allows concurrent input from multiple players with no queue ([AI Dungeon multiplayer FAQ](https://help.aidungeon.com/faq/do-you-support-multiplayer)). MUD architecture treats commands as real-time events into a continuous simulation as the standard, not an edge case ([Iron Realms — how MUD games work](https://www.ironrealms.com/mud-games/how-mud-games-work/)).

- **Outside combat**: any joined player may act at any time; the engine processes actions in real arrival order. No turn concept applies.
- **Once combat is declared**: real initiative (`1d10 + Reflexes`, per the ruleset spec), a turn-order cycle applies, out-of-turn actions are rejected. This is the one place a queue is earned — contested shared HP/damage state creates genuine resolution-order ambiguity that free-flowing input can't safely handle.
- Combat start/end are explicit, player-triggered events, not inferred from narration — an LLM narrator's own judgment about "did a fight just start" isn't a reliable trigger for a mechanical state change (a general LLM-reliability concern, not specific to any one project).

## Real-time transport: WebSocket

The real justification is **bidirectionality**, not narration streaming. Current (2026) consensus is that Server-Sent Events (SSE) is the dominant pattern for one-way server→client streaming — every major LLM provider (OpenAI/Anthropic/Google) streams narration tokens over SSE specifically ([APIScout 2026 real-time API guide](https://apiscout.dev/guides/sse-vs-websockets-vs-long-polling-realtime-api-2026)). SSE alone would suffice for streaming narration text. WebSocket is the correct choice because Nightwire also needs the reverse channel — player actions flowing server-ward and broadcasts reaching multiple connected clients — at the same real-time cadence, which SSE (one-directional) can't provide without pairing it with a separate request channel. A single bidirectional WebSocket connection carrying both directions is simpler than SSE-plus-something-else for this shape of app.

## Server-authoritative state, filtered per-client views

A real, independently-documented architecture pattern: the server decides what each client sees rather than broadcasting full world state to everyone. Gaffer On Games documents this as clients receiving "the state of your character and other players near you," not the full simulation ([Gaffer On Games — game networking](https://gafferongames.com/post/what_every_programmer_needs_to_know_about_game_networking/)); Coherence's networking docs describe the same server-authoritative filtering independently ([coherence server-authoritative setup](https://docs.coherence.io/1.3/manual/authority/server-authoritative-setup)).

Honest caveat: the documented cases are **proximity/interest-management** filtering (bandwidth/relevance — nearby vs. distant entities), not **privacy** filtering (hiding one player's own inventory/stats from another player who's right next to them in the fiction). Nightwire's use is a defensible generalization of the same "server decides what you see" principle, not an identical documented case — worth being precise about rather than overclaiming a 1:1 precedent. Concretely: each connected player receives their own full character sheet plus a redacted view of every other player (name, role, Health/Armor, visible conditions — not inventory, exact stats, or notes).

## AI GM / narrator backend: structured JSON output over native tool-calling

External evidence (not a single internal finding) supports this specifically for **local/open-weight models**: "the issue of unreliable JSON output primarily affects local open-source models" ([Structured Output as a Full Replacement for Function Calling](https://medium.com/@virtualik/structured-output-as-a-full-replacement-for-function-calling-430bf98be686)), corroborated independently by a 13-model local-LLM tool-calling evaluation ([jdhodges local-LLM tool-calling eval](https://www.jdhodges.com/blog/local-llms-on-tool-calling-2026-pt1-local-lm/)). Real nuance worth keeping precise: reliability tracks **training methodology and quantization**, not raw parameter count alone — "training methodology and architecture seem to matter more than raw parameter count" at typical local-deployment quantization levels. So the design default is: structured/constrained JSON output for the mechanical decision step on local models, not a blanket "small models are unreliable" claim.

- **Swappable backend**: local (Ollama) default, hosted API as a secondary option — the reliability argument above applies specifically to the local path; a hosted frontier model's native tool-calling doesn't carry the same documented risk, so the backend abstraction should let each implementation pick its own resolution mechanism rather than forcing structured-output everywhere.
- **A real reliability-measurement harness from the start** — deterministic, repeatable scenario runs against a real backend (`--repeat N`-style), not a single anecdotal test. Standard practice for multiplayer/game-server testing generally treats deterministic, seeded, repeatable runs as the baseline (see Testing, below) — the same discipline applied to narrator reliability specifically.

## Persistence: JSON file-per-session

Real precedent for this scale: modern MUD-adjacent projects use JSON documents as canonical world state per entity (town/NPC/quest/player profile), a genuine, current pattern, not merely "the simple option" ([MUD-Dev persistence discussion](http://www.disinterest.org/resource/MUD-Dev/1998q1/005285.html); confirmed on active community forums, [Top Mud Sites](https://topmudsites.com/forums/showthread.php?t=5785)). Larger-scale projects reach for Redis or a real database; for solo/LAN-scale play with no multi-tenant hosting requirement, flat JSON files remain a defensible, real choice at this scale, not a shortcut. A startup writability check (fail fast and loud if the store directory can't actually be written to, rather than a silent failure discovered mid-session) is a general reliability practice worth building in from the start, independent of any prior project's specific incident.

## Testing: deterministic seeded scripted clients

Standard, documented industry practice for multiplayer/real-time game testing, not a one-off pattern: "deterministic sessions that are seeded and runnable on every build," coordinating scripted clients to assert state convergence before real players hit an issue ([GameDriver multiplayer testing](https://gamedriver.ai/solutions/multiplayer); [Game Networking Demystified: State vs. Input](https://ruoyusun.com/2019/03/28/game-networking-1.html)). Applied here as: engine-level tests driven by a scripted/stub narrator (deterministic, no live model), full pytest coverage from the first commit, and the live-model reliability harness (above) as a separate, explicitly-non-deterministic-but-repeatable layer on top.

## What's deliberately deferred

- The exact envelope/message catalog — built alongside the features that need each one, not pre-declared speculatively.
- Combat's NPC-turn-autonomy question (does an NPC ever get a real mechanical turn slot, or only get referenced in initiative order) — a genuinely bigger, separate design question, not defaulted either way without its own pass.
